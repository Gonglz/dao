# 面向管理者的项目进度汇报 — 可选表达模板

**用途：** 面向非技术背景的负责人解释工程、研究或运营工作，
让听众理解问题、价值、当前结果和下一步，同时保留证据边界。

**边界：** 这只是汇报表达方式，不修改 Ticket 的权威性、
测试验收要求、仓库职责、生产授权或文档契约。
用户未要求管理层汇报时，不要强制套用。

## 六段式组织逻辑

1. **问题：** 之前哪里不符合预期？为什么重要？
2. **原因：** 为什么发生？把已经证实的原因与推测分开。
3. **措施：** 做了什么、核查了什么？为什么这样做？
4. **结果：** 现在改善了什么？有什么可核实的证据？
5. **进度：** 哪些已完成、正在进行、被阻塞、尚未开始？
6. **下一步和风险：** 还缺什么验证？是否需要负责人决策？

**一句话开场：**“我们此前发现〔问题及影响〕，目前确认／初步判断
原因是〔原因〕；采取了〔措施〕后，已经实现〔结果〕。
现阶段处于〔状态〕，下一步将〔具体行动〕。”

六段式是组织思路，不要求真的出现六个标题；能够合并时应合并，
避免为了模板而啰嗦。

## 可直接复制的 ChatGPT / Agent 提示词

按需填写少量字段即可：

```text
请以项目负责人的身份，面向没有技术背景的领导，
用简单、准确、自然的中文汇报项目进度，就像组会汇报。

汇报对象：<项目 / Ticket / Issue>
听众：<课题组导师 / 项目经理 / 非技术领导>
时长：<30 秒 / 2 分钟 / 5 分钟>
需要领导决定的事情：<无 / 具体决策>

如果可以读取仓库和任务状态，请先核对当前 Issue、代码、
测试、PR 和运行证据，不要仅凭旧聊天记录推断进度。
Issue 关闭、测试通过、PR 合并，都不能自动证明已经生产上线。

按以下逻辑组织：
1. 之前遇到了什么问题，对项目有什么影响？
2. 为什么会出现，哪些原因已确认，哪些只是推测？
3. 采取了什么解决措施，为什么采用这种办法？
4. 已经得到什么可核实的结果，结果覆盖多大范围？
5. 哪些完成、进行中、阻塞或尚未验证？
6. 接下来做什么、有什么风险、需要什么决策？

先讲结论和意义，再讲方法。尽量不用技术术语；必要时用一句
日常语言解释。主汇报中不要堆 Ticket 编号、路径、命令和测试日志，
这些放在补充材料里即可。

主汇报最多保留 2–3 个真正有意义的数字，并讲清数字代表什么。
不能编造数据、根因、日期、完成率或交付时间。
证据不足时直接说“尚未验证”。
严格区分：代码完成、本地测试通过、部署完成和生产验收通过。

输出：
A. 指定时长内可以直接念出来的汇报稿；
B. 用一句话概括当前进度；
C. 如有必要，补充领导可能追问的 2–3 个问题及简短回答。
```

## 长度参考

- **30 秒：** 一段话，约 150–230 个汉字，讲清核心进展和下一步。
- **2 分钟：** 约 350–550 个汉字，覆盖问题、行动、结果、
  当前状态和风险，适合普通组会。
- **5 分钟：** 可以增加原因验证、证据和取舍；
  技术细节仍放到附录中，不放在开头。

这是写作长度参考，不是需要机器检查的验收 Gate。

## 证据与表达约束

| 不准确的说法 | 更准确的表达 |
| --- | --- |
| “1,000 项测试通过，说明全部数据正确。” | “1,000 项本地测试通过；完整的数据质量验收还未完成。” |
| “有 8,000 个数据错误。”（实际是来源不明的文件） | “有 8,000 个文件的来源关系仍待确认，不能直接认定数据错误。” |
| “问题肯定是旧架构导致的。”（尚无证据） | “历史导入标准不一致是目前的解释方向；已经确认的事实是……” |
| “系统已经上线。”（只是 PR 合并） | “代码已合并，但尚未完成生产部署验证。” |

日常类比只在能降低理解难度时使用，一次一个即可，
不能把类比当成技术证据。

## 汇报前的自检

- 完全不了解仓库的人，能否用一句话复述原来的问题？
- 原因是已证实，还是明确标注为推测？
- 有没有区分“做了什么”和“证明达到了什么效果”？
- 每个“完成”是否有范围和证据？
- 尚未验证、尚未部署、仍有阻塞的地方是否明确？
- 下一步是否具体，能帮助负责人作决定？

需要技术深度时，另附 Issue、PR、验证记录、测试范围和风险；
不要把技术附录读成主汇报。
